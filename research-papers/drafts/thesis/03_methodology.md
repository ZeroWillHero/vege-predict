# Chapter 3: Methodology

## 3.1 Introduction to This Chapter

This chapter explains, in full detail and in plain language, exactly how this research was carried out — from the moment raw data was collected from government websites and weather services, all the way through to a trained, evaluated forecasting model that can be queried by an application. The goal of this chapter is that another researcher, or a reader without a deep machine learning background, should be able to read it and understand not just *what* was done, but *why* it was done that way, and *how* each piece connects to the next.

The chapter is organised to follow the actual order of work, because that order matters: a forecasting model is only as good as the data it is trained on, and the data is only as good as the process used to collect, clean, and combine it. So the chapter moves through six broad stages, in this order:

1. **Data collection** — where the raw numbers came from, and how they were fetched (Section 3.4).
2. **Data quality assurance** — how the raw data was checked for errors before being trusted (Section 3.5).
3. **Data integration and preprocessing** — how three separate data sources were combined into one clean dataset per vegetable (Section 3.6).
4. **Exploratory data analysis and feature engineering** — how the raw combined data was examined and then turned into the actual inputs a model can learn from (Sections 3.7–3.8).
5. **Model development and training** — the seven different forecasting approaches that were built, and exactly how each one was trained and evaluated (Sections 3.10–3.14).
6. **The prototype system** — how the trained models are served to an application (Section 3.15).

Before going into each stage, Section 3.2 explains the overall research approach and Section 3.3 gives a short, non-technical overview of the three data sources, so that the reader has the "big picture" before the detail. Section 3.9 lists every software tool and technology used in the project and explains, in plain terms, what each one does and why it was chosen. Section 3.16 covers the technical environment the work was carried out in, for reproducibility.

## 3.2 Research Design and Approach

This research follows a **quantitative, experimental, comparative design**. In plain terms, that means the study does not rely on opinions, interviews, or qualitative judgement to decide which forecasting approach is "best" — it builds several different forecasting models, feeds them all exactly the same data, tests them all using exactly the same evaluation rules, and then compares their numerical performance. Whichever model produces the smallest error on data it has never seen before is judged the best model for that vegetable.

This comparative approach was chosen for two reasons. First, the literature reviewed in Chapter 2 shows that no single modelling approach — whether a classical statistical model like SARIMA, or a modern machine learning model like Random Forest or XGBoost — is universally the best choice for every agricultural price series; the right choice depends on the specific market, the specific vegetable, and the specific data available. Second, this project's own proposal specifically calls for a comparison across model families (SARIMA, LSTM, Random Forest, XGBoost, and hybrid statistical–ML combinations), rather than committing to one model in advance. Building and fairly comparing several models is therefore not just good scientific practice here — it is the actual research question.

The overall flow of the work, from raw data to a usable forecast, looks like this:

```
Raw data collection (HARTI, CBSL, CEYPETCO, Open-Meteo)
        ↓
Data quality checks (missing weeks, outliers)
        ↓
Data integration (merge price + weather + fuel, per vegetable)
        ↓
Exploratory data analysis (trends, seasonality, distributions)
        ↓
Feature engineering (lags, rolling statistics, calendar, season)
        ↓
Model training (7 model families × 6 vegetables, walk-forward
                cross-validation + a final untouched holdout test)
        ↓
Evaluation and comparison (MAE, RMSE, MAPE, R², prediction intervals)
        ↓
Trained model artifacts saved to disk
        ↓
Prototype backend (FastAPI + PostgreSQL + Redis) serves the results
```

Every one of these stages is implemented as actual, runnable code in this project's repository (not done manually in a spreadsheet), which means the entire pipeline — from a freshly downloaded government PDF to a comparison table of seven models' accuracy — can be re-run automatically at any time as new weekly data becomes available. This reproducibility is itself a deliberate methodological choice, discussed further in Section 3.16.

## 3.3 Overview of the Data Sources

Before describing how each data source was collected in detail (Section 3.4), it is useful to step back and explain, in simple terms, *what* data this research actually uses and *why*. Three separate real-world data sources feed into every forecasting model built in this project:

**1. Historical vegetable prices.** This is the actual weekly wholesale and retail selling price of each of the six target vegetables — carrot, brinjal, pumpkin, cabbage, snake gourd, and leeks — going back as far as the year 2000 for some vegetables. This is the "target" data: the number the models are trying to predict for next week. Retail price (the price a consumer actually pays) was chosen as the specific figure to forecast, because it is the number most directly useful to the farmers and traders this project is ultimately meant to help, rather than the wholesale price which is one step further removed from what shoppers and small sellers experience.

**2. Weather data.** Vegetable prices are strongly affected by growing conditions: a drought or an unusually heavy monsoon can destroy a harvest and send prices up weeks later, while good weather can produce a glut that crashes prices. This project collects weekly average temperature and average rainfall for every district in Sri Lanka, and matches each vegetable to the specific district where it is predominantly grown, so that the weather data used to help forecast a vegetable's price reflects the actual growing conditions that vegetable experienced, not a generic national average that would dilute the real signal.

**3. Fuel prices.** In Sri Lanka's supply chain, vegetables are grown up-country or in specific low-country zones and then transported by lorry to markets across the island. Diesel is the fuel that powers that transport, so a rise in diesel price raises the cost of getting vegetables to market, which tends to push retail prices up independently of the harvest itself. This project therefore includes the weekly diesel price as a third input.

These three sources were chosen deliberately, not arbitrarily: they match the same set of exogenous (external) drivers — rainfall, temperature, and fuel price — that prior Sri Lanka-specific research (Ranaweera, Rathnayake, & Ananda, 2023) found to be the most useful additional signals for forecasting vegetable prices in this exact market, and they match the general lesson from the wider literature (Weerasekara et al., 2026; Shree Sanjay & Janarthanan, 2025) that adding the *right* external features tends to improve forecasting accuracy more than switching to a fancier model architecture does. Two further data sources — satellite crop-condition imagery (NDVI) and IoT sensor readings from farms — are part of this project's longer-term objectives (Chapter 1) but have not yet been collected; this is explained further in Section 3.4.5.

## 3.4 Data Collection

This section explains, source by source, exactly where the raw numbers in this project came from and how they were physically fetched. This is not a small detail: unlike many student research projects that download a single ready-made CSV file from Kaggle and stop there, this project builds and runs its own automated data-collection scripts against real government and industry websites, because no single ready-made dataset covering Sri Lankan vegetable prices, weather, and fuel prices together and up to date already existed.

### 3.4.1 Vegetable Price Data

The primary source of historical vegetable price data is the **Hector Kobbekaduwa Agrarian Research and Training Institute (HARTI)**, a Sri Lankan government research institute that publishes a **Weekly Food Commodities Bulletin** — a PDF document released every week containing wholesale and retail price tables for a wide range of food items, collected from markets across the country.

Fetching this data is not as simple as downloading one file, because HARTI publishes a *new* PDF every week, and the exact web address (URL) of each week's bulletin is not predictable in advance — the filename spacing and capitalisation is inconsistent from one week to the next (for example, "Final English Bulletin - week 25.pdf" one week and "Final  English Bulletin - Week 24.pdf" the next). To handle this, this project built a dedicated Python script (`src/pipeline/scrapers/harti_prices.py`) that:

1. Downloads HARTI's bulletin index page and searches it for the actual link matching a given week and year, rather than guessing a filename pattern.
2. Downloads that week's PDF bulletin.
3. Uses a PDF-table-extraction library (`pdfplumber`) to locate and read two specific tables inside the PDF: "Table 06: Selected Markets: Wholesale Price of Vegetables" and "Table 07: Selected Markets: Retail Price of Vegetables".
4. Parses each table cell, which is reported as a price *range* across multiple markets (for example, "120.00−150.00") rather than a single number, and averages the midpoints of all reporting markets to produce one national weekly figure per vegetable.
5. Maps HARTI's own vegetable names to this project's naming convention (for example, HARTI's "Brinjal" becomes this project's "BRINJALS", matching the existing raw data file's format).

HARTI's wholesale table does not cover pumpkin or snake gourd, so for those two vegetables the wholesale price is left blank from this source — this does not affect the actual forecasting target, which is retail price, and HARTI's retail table does cover all six target vegetables including leeks.

A second, complementary scraper (`src/pipeline/scrapers/cbsl_prices.py`) reads the **Central Bank of Sri Lanka's (CBSL) Daily Price Report**, another official PDF published more frequently than HARTI's bulletin. This source was investigated as a way to fill in data faster, but it was found (by directly inspecting a real report) that CBSL's daily report does not track leeks at all, so it cannot fully replace HARTI's bulletin as the primary source — it exists in the pipeline as a secondary, corroborating source rather than the main one. HARTI was therefore selected as the primary price source specifically because it is the only one of the two that reports all six target vegetables at the correct weekly cadence.

The scraper runs in a **"strategic" incremental mode**: rather than re-downloading and re-parsing every historical bulletin every time it runs, it keeps track of which weeks have already been fetched and only downloads new, not-yet-seen bulletins. This is both faster and gentler on HARTI's website, and it is what makes it realistic to re-run this pipeline every week without manual effort — a foundation piece for the automated retraining work planned for a later phase of this project (see the note on future work in Section 3.4.5 and the MLOps discussion in Chapter 2, Section 2.10).

The resulting raw file, `data/raw/vegetable_prices/vegetable_prices.csv`, contains one row per (vegetable, week) pair with four columns: the vegetable name, the week's start date, the wholesale price, and the retail price. As currently collected, this file spans from **3 January 2000** through to the most recent available HARTI bulletin.

### 3.4.2 Fuel Price Data

Diesel prices come from the **Ceylon Petroleum Corporation (CEYPETCO)**, Sri Lanka's state-owned fuel supplier, via a historical price table published at `ceypetco.gov.lk/historical-prices/`. Unlike HARTI's data, this source is a plain HTML table rather than a PDF, which makes it more straightforward to parse — but it has a different structural quirk: CEYPETCO does not publish one row per week. Instead, it publishes one row per price *revision* — that is, one row every time the government changes the diesel price, which can be days or months apart, not on a fixed weekly schedule.

To turn this into the weekly series the rest of the project needs, the fuel-price scraper (`src/pipeline/scrapers/cpc_fuel.py`) applies a **forward-fill**: for every Monday (the start of each week in this project's data, matching the convention used for prices and weather), it looks up whichever diesel price revision was most recently in effect on or before that date, and uses that as the week's price. This correctly reflects reality — the diesel price a transporter actually pays in a given week is whatever the current rate is, not an average of old and new rates — and it was verified directly against a real published news report (the price revision effective 31 May 2026 reads Rs. 407 per litre in this project's scraped data, exactly matching the publicly reported figure for that date).

The specific column extracted is CEYPETCO's "LAD" (Lanka Auto Diesel) price, since diesel — not petrol — is the fuel that powers the lorries and trucks that move produce from farms to markets. Petrol prices were considered and explicitly excluded from this project's data entirely (not merely left unused), because petrol has no meaningful link to the vegetable supply chain, while diesel is the direct transport-cost driver identified in the literature (Ranaweera et al., 2023).

The resulting file, `data/raw/fuel/fuel_data_weekly.csv`, contains one row per week with two columns: the week's date and that week's diesel price, currently spanning from **5 January 2015** onward — this start date is later than the price data's start date because CEYPETCO's historical revision table does not extend as far back, and this project's data alignment step (Section 3.6) accounts for that gap explicitly.

### 3.4.3 Weather Data

Weather data — weekly average temperature and weekly average rainfall — comes from **Open-Meteo**, a free, publicly available historical weather archive API that provides daily weather records for any geographic coordinate going back to 2014. This project fetches data for the representative town or city coordinates of **all 25 administrative districts of Sri Lanka** (`scripts/fetch_weather_openmeteo.py`), not just the six districts actually used by the target vegetables, so that the raw weather dataset is complete and reusable if the project's vegetable list or district mapping changes in the future.

For each district, the script downloads a daily record of maximum temperature, minimum temperature, and total precipitation, and then aggregates these daily values into weekly figures in two ways:

- **Average temperature** for a week is calculated as the mean, across the seven days of that week, of each day's (maximum + minimum) ÷ 2 — a standard way of estimating a day's typical temperature from its extremes.
- **Average rainfall** for a week is the mean of each day's total precipitation that week.

Because vegetable prices are reported nationally (one price per vegetable per week, not one price per district), but weather genuinely differs from one part of the island to another, this project maps each vegetable to a **single representative growing district** that reflects Sri Lanka's structural division between up-country and low-country agriculture:

| Vegetable | Growing zone | Representative district |
|---|---|---|
| Carrot | Up-country | Nuwara Eliya |
| Leeks | Up-country | Nuwara Eliya |
| Cabbage | Up-country | Nuwara Eliya |
| Brinjal | Low-country | Matale |
| Pumpkin | Low-country, dry zone | Anuradhapura |
| Snake gourd | Low-country, dry zone | Kurunegala |

This mapping follows the up-country/low-country growing-zone structure documented in the literature (Weerasekara et al., 2026) and the specific market centres used in the closest prior Sri Lankan study (Ranaweera et al., 2023). It is stored as configuration data (in `configs/config.yaml`) rather than hard-coded inside the program logic, specifically so that it can be revisited or refined later — for example if a future version of this project wanted to average weather across two or three districts per vegetable instead of one — without needing to change any code.

The resulting file, `data/raw/weather/weather.csv`, contains one row per (district, week) pair, currently spanning from **30 December 2013** to the present.

### 3.4.4 Data Sources Not Yet Collected

Chapter 1 sets out five objectives for this project, and the first of them calls for a dataset that also includes satellite crop-condition imagery (specifically, the Normalized Difference Vegetation Index, or NDVI, derived from Sentinel-2 satellite imagery via Google Earth Engine), IoT sensor readings from farms, and farmer behavioural survey data. These three additional sources have not yet been collected, and this is a deliberate, acknowledged scoping decision rather than an oversight.

The reason is practical: satellite NDVI collection requires setting up authenticated access to Google Earth Engine and deciding which specific farm plots or growing regions to sample imagery from; IoT sensor data requires either physical hardware deployed on real farms or a partnership with an organisation that already has such sensors installed; and behavioural survey data requires designing a survey instrument and actually reaching farmers to complete it. Each of these is a substantial sub-project in its own right. Rather than attempt all of them at once and deliver each poorly, this phase of the research deliberately completed and thoroughly validated the price/weather/fuel forecasting pipeline first — the recent literature review (Chapter 2, Section 2.8) also confirms that satellite and IoT signal for vegetable-type crops has been shown to carry useful forecasting information in other studies (Darra et al., 2023; Ayall et al., 2025), which supports this as a promising and well-motivated next step rather than a speculative one. This remains explicitly future work, discussed further in the Conclusion.

## 3.5 Data Quality Assurance

Automatically scraping data from PDF documents and web pages, week after week, without a human checking every number by eye, carries a real risk: a single mis-read PDF table, a webpage layout change, or a genuine one-off reporting error at the source could silently introduce a wrong number into the dataset, and every model trained afterwards would learn from that error without anyone noticing. This is not a hypothetical concern — Jain, Marvaniya, Godbole, and Munigala (2020), in their study of automated crop-price data pipelines in India, specifically found that manually entered daily crop prices are themselves error-prone (missing entries, incorrect values), and argued that data-quality monitoring must be treated as a precondition for reliable forecasting, not an afterthought.

To guard against this, this project built a dedicated data quality module (`src/pipeline/quality_checks.py`) that sits between newly collected data and the rest of the pipeline, and performs two kinds of checks before any new data is accepted:

**1. Missing week detection.** For any time series that is supposed to have one row per week, the module checks whether every expected Monday between the earliest and latest date actually has a row, and reports any gap. This catches situations where a bulletin was never published for a given week, or where a scraper silently failed to fetch one week's data without raising an obvious error.

**2. Outlier detection.** For each numeric value (a price, a temperature, a rainfall figure), the module flags a row as suspicious if any of the following is true:
   - The value is negative, or zero when zero is not a plausible reading for that variable (a price of zero, for example, is almost always a data error rather than a genuine free vegetable).
   - The value has changed by more than 150% from the previous week for that same vegetable or district — a much larger single-week jump than genuine price or temperature movement would normally produce.
   - The value is more than five standard deviations away from that vegetable's or district's own historical average (a "z-score" check) — a large statistical outlier relative to that specific series' normal range.

These two thresholds (150% week-over-week change, and five standard deviations) were set deliberately loose rather than tight. This is because Sri Lankan vegetable prices genuinely do move very fast in reality — the project's own later results (Chapter 4) show SARIMAX producing a negative R² on a recent, highly volatile holdout period, which is a real market phenomenon, not a data-quality issue. The point of these checks is to catch data *entry or extraction* errors, not to flag or reject real, dramatic price volatility, which is exactly the kind of behaviour this research is trying to forecast.

One deliberate exception to the percentage-change check is rainfall: because weekly rainfall is naturally "bursty" and often close to zero (for example, jumping from 0.3mm one week to 1.6mm the next is a 433% "change" in percentage terms but is not remotely unusual weather), the percentage-change check is switched off for rainfall specifically, and only the z-score check (which compares against that district's own historical spread, not a percentage) is used for it.

When new data is merged into an existing raw file, any row that is flagged by these checks is rejected and excluded from the merge (with the specific reason for rejection recorded), while rows that pass are appended, and any row that duplicates an existing (date, vegetable) or (date, district) pair is treated as an update rather than a duplicate entry. This quality-checking module can also be run on its own, in a read-only "audit" mode (`python src/pipeline/quality_checks.py --audit`), to produce a report of any missing weeks or flagged values already present in the existing raw data files, which was used during this project to confirm the historical data collected via the scrapers described in Section 3.4 was clean before it was used for any model training.

## 3.6 Data Integration and Preprocessing

Once the three raw data sources described in Section 3.4 have passed the quality checks in Section 3.5, they still exist as three separate files, each with a different structure, a different set of columns, and — critically — a different date range. The next stage of the pipeline (`src/data_processing/build_dataset.py`) combines them into one clean, ready-to-use dataset per vegetable. This step performs four operations, in order:

**1. Filtering to one vegetable.** The raw price file contains all six vegetables mixed together; this step selects just the rows for the vegetable currently being processed, using the vegetable name mapping described earlier (for example, this project's internal name "brinjal" maps to the raw file's "BRINJALS").

**2. Selecting the correct weather district.** Using the vegetable-to-district mapping from Section 3.4.3, this step selects only the weather rows for that vegetable's representative growing district, discarding the other 24 districts' rows for this particular vegetable's dataset.

**3. Merging on date.** The filtered price rows, the filtered weather rows, and the (nationwide) fuel-price rows are joined together using each row's week-start date as the matching key, so that each resulting row represents one specific week and contains that week's retail price, wholesale price, average temperature, average rainfall, and diesel price, all in a single row.

**4. Aligning to a common date range.** The three raw sources do not all cover the same historical period — the fuel data, for instance, only begins in January 2015, well after the price data begins in January 2000, because CEYPETCO's public historical-revision table does not go back further. Rather than allow rows with missing fuel data at the start of the series, the merged dataset is deliberately clipped to the overlapping window where genuine data exists across *all three* sources at once. This alignment window is stored explicitly in the project's configuration file rather than computed silently, so that it is always clear exactly which weeks are included and why, and so that it can be re-checked and widened as new data accumulates.

The result of this process is one clean CSV file per vegetable, saved under `data/processed/`, with no missing values anywhere, and containing exactly the columns needed for the next stage: date, retail price, wholesale price, average temperature, average rainfall, and diesel price. As of the most recent data update, each vegetable's processed file contains just under 600 weekly rows, covering the period from January 2015 through to the most recent available week — this figure will continue to grow by one row per vegetable every week as the data-collection scrapers described in Section 3.4 are re-run.

It is worth being explicit about why this two-stage separation — raw data collection and quality-checking (Sections 3.4–3.5) kept entirely separate from the merging-and-alignment step described here — was chosen as a design principle, rather than doing everything in one combined script. Keeping these stages separate means that each raw source can be re-fetched, re-checked, and re-validated completely independently of the others, and the merging step can always be safely re-run from scratch on the current raw files without needing to re-download anything, which makes the whole pipeline both easier to debug when something goes wrong and far cheaper to re-run regularly.

## 3.7 Exploratory Data Analysis

Before any feature engineering or model training was attempted, the merged, cleaned dataset for each vegetable was explored visually and statistically, in a dedicated notebook (`notebooks/01_data_exploration.ipynb`), to build an actual understanding of what the data looks like — rather than jumping straight to modelling and treating the data as an unexamined black box. This exploratory analysis served three purposes.

**First, understanding the trend and volatility of each vegetable's price series.** Plotting retail price against time for each of the six vegetables makes visible, at a glance, how volatile Sri Lanka's vegetable prices genuinely are — prices can rise or fall substantially within a single week, consistent with the import-isolated, weather- and fuel-sensitive market structure described in Chapter 1. This confirmed, before any model was built, that a naive model assuming smooth, gradual price changes would be a poor fit for this market, and that models capable of reacting to sharp, irregular movements (as opposed to assuming pure linear trend) would likely be needed.

**Second, checking for seasonal patterns.** Because Sri Lankan agriculture is structured around two monsoon-driven cultivation seasons — *Maha* (October to April) and *Yala* (May to September) — the exploratory analysis specifically examined whether average prices differ systematically between these two seasons for each vegetable, and whether a recurring yearly (52-week) pattern is visible in the price series. This examination is what justified including both a seasonal component in the SARIMAX model (Section 3.10.1) and an explicit Maha/Yala season flag as an engineered feature (Section 3.8).

**Third, examining the relationship between price and the exogenous variables.** The exploratory notebook also plotted retail price alongside rainfall, temperature, and diesel price over time, and computed simple correlation statistics between them, to sanity-check — before relying on it in a model — that these variables actually appear to move together with price in the expected direction (for example, that spikes in diesel price tend to coincide with or precede spikes in retail price). This step is what is generally called exploratory data analysis, or EDA: looking at the data with plots and summary statistics *before* fitting any model, specifically to catch anything unexpected (an implausible value, a missing pattern, a variable that turns out not to matter) early, rather than discovering it only after a model has already been built and produces confusing results.

## 3.8 Feature Engineering

A raw weekly record of "retail price, wholesale price, temperature, rainfall, diesel price" is not, by itself, enough information for most machine learning models to make a good forecast — machine learning models generally need to be given explicit, numeric clues about *patterns over time*, because (unlike a human looking at a chart) they do not automatically understand that "the price four weeks ago" or "the price is usually higher in December" might be relevant unless that information is presented to them as its own input column. The process of creating these additional, more informative input columns from the raw data is called **feature engineering**, and it is implemented once, in a single shared module (`src/features/feature_engineering.py`), so that every one of the seven model families described later in this chapter is trained on an *exactly identical* set of input features — this matters because it means that when one model outperforms another later in this study (Chapter 4), the difference can be attributed to the model itself, not to one model secretly having access to better input data than another.

Four categories of engineered feature are added to every vegetable's dataset:

**1. Lagged price features.** These are simply the vegetable's own retail price from previous weeks, explicitly copied into new columns: the price 1 week ago, 2 weeks ago, 4 weeks ago, and 8 weeks ago. In plain terms, this gives the model direct access to "what was the price recently," which is one of the single strongest predictors of "what will the price be next," since prices rarely change completely at random from one week to the next.

**2. Rolling statistics.** These summarise recent price *behaviour*, rather than just a single past value: the average and the standard deviation (a measure of how much the price has been fluctuating) of retail price over the trailing 4, 8, and 12 weeks. A model can use these to tell, for instance, whether the price has been generally stable and slowly trending, or wildly bouncing around — information that a single lagged value cannot capture on its own. To avoid a subtle but serious error called **data leakage** — accidentally letting a model "see" information from the future, including the very value it is trying to predict — every rolling statistic is calculated only from prices *before* the current week, never including the current week's own price.

**3. Calendar and season features.** The month number, the ISO week-of-year number, the calendar quarter, and a simple yes/no flag for whether the current week falls in the Maha (October–April) or Yala (May–September) growing season are all added as explicit numeric inputs. These let a model learn recurring calendar-based patterns directly — for example, that a particular vegetable's price tends to be systematically higher or lower during a specific part of the year — without needing to infer that pattern indirectly from price history alone.

**4. Exogenous features, contemporaneous and lagged.** The current week's rainfall, temperature, and diesel price are included directly (these are the "exogenous," or externally driven, variables described in Section 3.3), and each of them is *also* included lagged by one week. This lagged version matters because weather's effect on price is not always immediate — a drought this week might not show up as a price increase until the following week or two, once existing stock in the supply chain runs down — so giving the model both the current and the one-week-prior value lets it learn whichever timing relationship actually exists in the data, rather than assuming the effect is always instantaneous.

After these features are added, the very first several weeks of each vegetable's series inevitably have missing values for some of the longer lag and rolling-window features (there is, for example, no "12-week rolling average" available for the very first week of data, since 12 weeks of prior history do not yet exist). These "warm-up" rows are dropped entirely rather than filled in artificially, since any artificial fill-in value would itself be a form of fabricated data. After this warm-up period is removed, roughly 571 usable weekly rows per vegetable remain from the aligned dataset described in Section 3.6, plenty for the walk-forward cross-validation and holdout evaluation scheme described in Section 3.12.

Finally, the specific list of columns actually passed into a model as its "features" is derived programmatically from the resulting dataframe — automatically taking every column except the date, the raw wholesale price (kept in the file for reference, but deliberately excluded from the feature set because it is so closely correlated with the retail-price target that including it would let a model trivially "cheat" rather than genuinely learn from the weather, fuel, and seasonal signals), and the target column itself — rather than being typed out by hand in each model's training script. This ensures that if a new feature is ever added to the shared feature-engineering module in the future, every model family automatically receives it without needing separate code changes in seven different places.

## 3.9 Technologies and Tools Used

This section lists, and briefly explains in plain terms, every significant piece of software technology used to carry out this research, since a reader unfamiliar with the modern data science and software ecosystem may not recognise every name.

**Programming language and core data-handling libraries:**

- **Python 3.13** — the programming language the entire project is written in. Python was chosen because it is the standard language for both data science and machine learning research, with the largest ecosystem of ready-made, well-tested libraries for exactly this kind of work.
- **pandas** — a library for loading, filtering, joining, and reshaping tabular data (data organised in rows and columns, like a spreadsheet). Every CSV file this project reads or writes — raw prices, raw weather, raw fuel data, processed per-vegetable datasets, results tables — is handled through pandas.
- **NumPy** — a library for fast numerical array computation, used underneath pandas and directly for the mathematical operations behind the evaluation metrics (Section 3.13) and the prediction-interval calculation (Section 3.14).
- **PyYAML** — used to read the project's single configuration file (`configs/config.yaml`), where every hyperparameter, file path, and data-alignment date used throughout the project is stored, so that these values live in one human-readable place rather than being scattered and hard-coded across many Python files.

**Data collection libraries:**

- **requests** — used by the scrapers (Section 3.4) to download web pages and files (PDFs, HTML tables) over the internet from HARTI, CBSL, CEYPETCO, and Open-Meteo.
- **pdfplumber** — used specifically to extract structured tables of numbers out of the HARTI and CBSL PDF bulletins, which are ordinary formatted documents, not machine-readable data files, and would otherwise require a person to manually type the numbers out.

**Statistical and machine learning modelling libraries:**

- **statsmodels** — provides the SARIMAX statistical time-series model (Section 3.10.1).
- **scikit-learn** — provides the Random Forest model (Section 3.10.3), the data-standardisation tool used to prepare inputs for the LSTM (Section 3.10.2), and several general-purpose utilities used throughout the evaluation pipeline.
- **XGBoost** and **CatBoost** — two separate, widely used "gradient boosting" libraries, each providing one of the tree-based machine learning models compared in this study (Sections 3.10.4–3.10.5), and each also used as the "residual model" half of one of the two hybrid models (Section 3.10.6).
- **TensorFlow / Keras** — the deep learning framework used to build and train the LSTM neural network model (Section 3.10.2).
- **Optuna** — a hyperparameter-optimisation library included in this project's dependencies for future tuning work; the specific hyperparameter values actually used for each model in this phase of the research (listed throughout Section 3.10) were set from a combination of literature precedent and manual experimentation, documented directly in `configs/config.yaml`.

**Analysis, visualisation, and reproducibility tools:**

- **Jupyter Notebook** — used for the exploratory data analysis (Section 3.7) and for producing the final forecast-versus-actual comparison charts (Chapter 4), because a notebook lets code, its output, and explanatory text sit together in one document, which is well suited to exploratory, visual work.
- **Matplotlib** and **Seaborn** — the two charting libraries used to produce every plot in this project, from the exploratory price-trend charts to the final forecast-versus-actual figures.

**Prototype backend and infrastructure technologies** (used to serve the trained models to an application, described fully in Section 3.15):

## 3.10 Forecasting Model Development

With a clean, feature-engineered dataset in place (Sections 3.6–3.8), this project trains and compares **seven distinct forecasting approaches** for each of the six target vegetables — 42 separate trained models in total. This section explains each of the seven approaches individually, deliberately starting each explanation from first principles in plain language, before giving the exact technical configuration used.

The seven model families fall into three broad groups: one classical statistical model (SARIMAX), one deep learning model (LSTM), three tree-based machine learning models (Random Forest, XGBoost, and CatBoost), and two hybrid models that combine the statistical model with a machine learning model. This spread was chosen specifically to match the mandate in this project's original proposal — comparing statistical, machine learning, and hybrid approaches head-to-head — while CatBoost and its hybrid variant are included as an additional, extended baseline beyond the minimum required set, since they represent another modern, competitive gradient-boosting approach worth including in a thorough comparison.

### 3.10.1 SARIMAX

**In plain terms:** SARIMAX is a classical statistical technique for forecasting a number that changes over time by learning three things directly from its own history: its overall trend (is it generally rising, falling, or flat), its seasonal pattern (does it tend to repeat a similar shape every year), and how much it tends to bounce around from a recent, short-term rise or fall. The name is an acronym: "Seasonal AutoRegressive Integrated Moving Average with eXogenous regressors." Unlike the machine learning models described later in this chapter, SARIMAX makes an explicit mathematical assumption about how the series behaves (it assumes a broadly linear relationship between a value and its own recent past), which makes it fast to fit and easy to interpret, but potentially too simple for a market as volatile and irregular as Sri Lanka's vegetable prices — a limitation discussed further in the literature review (Chapter 2, Section 2.2) and confirmed directly by this project's own results in Chapter 4.

**Why it was included:** SARIMAX and its non-seasonal ancestor, ARIMA, are the long-standing baseline in agricultural price forecasting research, and remain a meaningful point of comparison precisely because they represent "the traditional way this problem has usually been approached" before machine learning became common. SARIMAX specifically (rather than plain SARIMA) also allows external variables to be included as inputs, which lets it use the same weather and fuel data as every other model in this study, rather than forecasting price from its own history alone.

**How it was configured.** Two structural settings must be chosen for any SARIMAX model: its non-seasonal order — usually written (p, d, q) — and its seasonal order — usually written (P, D, Q, s). In this project:

- The **seasonal period, s, is fixed at 52**, since the data is weekly and a year contains 52 weeks — this tells the model to look for a pattern that repeats roughly once a year.
- The **seasonal order is fixed at (1, 0, 1, 52)** for every vegetable. A seasonal differencing value of 1 (meaning "compare this year's value to the same week last year, then model the resulting difference") was tried during development, but was found empirically to make out-of-sample forecasts diverge to implausible values, because with only around ten years of training data, there simply are not enough repeated yearly cycles for that stronger form of seasonal adjustment to be estimated reliably. A value of 0 (no seasonal differencing, but still allowing a seasonal autoregressive and moving-average relationship) was found to be stable and was kept.
- The **non-seasonal order (p, d, q) is chosen separately for each vegetable**, using a systematic search rather than a single fixed guess. This search (implemented in `scripts/select_sarimax_order.py`) follows the standard statistical approach for this kind of model, known as **Box–Jenkins order selection**: every combination of p and q from 0 to 2 (with d fixed at 1, since regular, non-seasonal differencing was already established as necessary for this data) is fit on the vegetable's full price history, and the combination that produces the lowest **Akaike Information Criterion (AIC)** — a standard statistical score that rewards a model for fitting the data well while penalising it for being unnecessarily complex — is selected as that vegetable's order. This produced the following per-vegetable orders, all somewhat richer than the initial literature-precedent starting point of (1, 1, 1): carrot (0, 1, 2); brinjal (2, 1, 2); pumpkin (2, 1, 2); cabbage (2, 1, 2); snake gourd (2, 1, 2); leeks (1, 1, 2).

It is important to be transparent about a subtlety here, discussed in full in Chapter 4: AIC measures how well a model fits the data it was *trained* on (in-sample fit), not how accurately it forecasts genuinely new, unseen future weeks (out-of-sample accuracy). This project's results show that the AIC-selected order does not uniformly improve holdout forecast accuracy compared to the simpler starting-point order — it helps substantially for some vegetables and slightly hurts others. This is an expected and well-documented property of AIC, not a flaw in the search process; it is precisely why AIC is used here only to choose SARIMAX's own internal structure, while the separate, larger question of "which of the seven model families is most accurate" (Section 3.14) is always answered using actual holdout forecast error instead.

The three exogenous regressors fed into SARIMAX are the current week's average rainfall, average temperature, and diesel price. One further technical setting, `simple_differencing`, was tested during development purely to speed up model fitting, but was found to break the model's ability to correctly extend its exogenous inputs into the future when forecasting — producing forecasts that swung to wildly unrealistic values — and was reverted; this is recorded as a known implementation gotcha in the project's own internal documentation, to prevent it from being accidentally re-introduced later.

Finally, a specific technical engineering problem is worth documenting here because it shaped how SARIMAX is actually saved to disk: a fully fitted SARIMAX model object, saved directly using Python's standard object-serialisation tool, balloons to roughly 320 megabytes per vegetable, because — due to the 52-week seasonal period — it carries the model's complete internal filtering history. This project instead saves a lightweight custom artifact containing only the model's final fitted parameters and a small history frame, and reconstructs the full model from those parameters only when a forecast is actually needed. This was directly verified to produce forecasts identical, down to the decimal, to saving the full model object, while reducing the saved file size from roughly 320 megabytes to roughly 20 kilobytes per vegetable — a reduction of well over ten-thousand-fold with no loss of forecasting accuracy.

### 3.10.2 LSTM (Long Short-Term Memory Neural Network)

**In plain terms:** An LSTM is a type of artificial neural network — a machine learning model loosely inspired by how networks of neurons process information — specifically designed to learn patterns in *sequences* of data, such as a series of weekly prices, by carrying forward a kind of internal "memory" from one time step to the next as it reads through the sequence. This lets it, in principle, learn more complex, non-linear relationships across longer stretches of history than a classical statistical model like SARIMAX can easily represent — for example, a pattern where an unusual weather event several weeks ago combines with a seasonal effect and a recent price trend in a way that is not a simple straight-line relationship.

**How it was configured.** This project's LSTM is a "stacked" network with two LSTM layers, each with 64 units (a unit is one of the network's individual memory-carrying components — more units generally means more capacity to learn complex patterns, at the cost of needing more data and more computation), and a dropout rate of 0.2 between layers. Dropout is a standard technique that randomly ignores 20% of the network's internal connections during each training step, which forces the network to not over-rely on any single internal pathway and generally makes it generalise better to new data instead of simply memorising the training data it has already seen.

The model is trained on sequences of 30 consecutive weeks of history at a time (so, to predict one week's price, it looks at the preceding 30 weeks of price and exogenous data together), using the Adam optimisation algorithm (a standard, widely used method for gradually adjusting a neural network's internal numbers during training so that its predictions improve) with a learning rate of 0.001, in batches of 32 sequences at a time, for up to 100 passes over the training data. Because all of this project's other models work directly with raw-scale numbers (prices in the hundreds, temperatures in the twenties), but neural networks generally train more reliably when all of their inputs are on a similar numeric scale, every input to the LSTM is first standardised (rescaled to have a mean of zero and a standard deviation of one) using a scaler that is fit only on that fold's training data and then applied unchanged to the corresponding test data — this avoids a subtle form of data leakage where information about the test period's own scale could otherwise leak backward into training.

Training does not always run the full 100 passes: an "early stopping" rule halts training if the model's error on its own training data stops improving for 10 consecutive passes, and restores the network's best-performing internal state from during training, rather than whatever state it happened to end training in — an important refinement given that neural network training can occasionally continue past the point where it is genuinely still improving.

Because the LSTM's internal starting values are set partly at random when training begins, it is worth being explicit that the LSTM is the one model family in this comparison whose results can vary slightly between two identical re-runs on the same data — every other model family in this study (SARIMAX, Random Forest, XGBoost, CatBoost, and the two hybrids) is fully deterministic given the same input, always producing exactly the same result. This is a genuine, expected property of neural networks, not a bug, and is noted explicitly wherever LSTM's results are reported in Chapter 4.

### 3.10.3 Random Forest

**In plain terms:** A Random Forest is a machine learning model built from many individual **decision trees** — a decision tree is a simple model that predicts a value by asking a sequence of yes/no-style questions about the input features (for example: "was last week's price above 150? If yes, was rainfall above 20mm? ...") and arriving at a prediction at the end of that chain of questions. A single decision tree, on its own, tends to overfit — it can become extremely good at predicting the exact data it was trained on while performing poorly on new data, because it can end up asking overly specific questions tailored to quirks in that particular training set. A Random Forest solves this by building many different decision trees (hundreds, in this project's case), each trained on a slightly different random subset of the training data and features, and then averaging all of their individual predictions together. This averaging tends to cancel out each individual tree's specific quirks while keeping the genuine, shared patterns that most of the trees agree on — a general machine learning strategy known as **ensemble learning**.

**How it was configured.** This project's Random Forest uses 500 individual trees, each limited to a maximum depth of 10 (meaning no tree is allowed to ask more than 10 questions in a row before making its prediction, which limits how overly specific any single tree can become), and each "leaf" (final answer node) of every tree must be supported by at least 2 training examples, which similarly discourages any tree from making a prediction based on a single, possibly unrepresentative data point. Random Forest is trained directly on the full engineered feature set described in Section 3.8 — the lagged prices, rolling statistics, calendar features, and exogenous variables — with no additional preprocessing needed, since tree-based models, unlike neural networks, do not require their inputs to be rescaled to a common numeric range.

### 3.10.4 XGBoost

**In plain terms:** XGBoost ("eXtreme Gradient Boosting") is, like Random Forest, built from many decision trees combined together — but where Random Forest builds all of its trees somewhat independently and then averages them, XGBoost builds its trees **one after another, in sequence**, where each new tree is specifically trained to correct the mistakes that all of the previous trees, combined, are still making. This general strategy is called **gradient boosting**. In practice, this sequential, error-correcting approach often lets gradient-boosted models like XGBoost achieve slightly higher accuracy than a Random Forest on the same data, though it can also be somewhat more prone to overfitting if not carefully tuned, since each tree is deliberately chasing the specific errors of the model so far.

**How it was configured.** This project's XGBoost model uses 500 sequential trees, each limited to a maximum depth of 6 (shallower than the Random Forest's trees, which is typical for gradient boosting, since each individual tree in a boosted sequence is meant to make a smaller, more targeted correction rather than a large independent prediction), and a "learning rate" of 0.05 — a setting that controls how large a correction each new tree is allowed to make; a smaller learning rate makes training more gradual and generally more stable, at the cost of needing more trees to reach the same overall accuracy. Like Random Forest, XGBoost is trained directly on the full engineered feature set with no additional rescaling needed.

### 3.10.5 CatBoost

**In plain terms:** CatBoost is another gradient-boosting library, built on the same general sequential, error-correcting idea as XGBoost, but with a somewhat different internal approach to how it builds each tree and calculates its corrections, which in some research has been found to perform particularly well without needing extensive manual tuning. It is included in this study as a second, independent gradient-boosting implementation, beyond what this project's original proposal strictly required, specifically to make the model comparison in Chapter 4 more thorough.

**How it was configured.** This project's CatBoost model is trained for 1,000 iterations (CatBoost's term for the number of sequential trees added), with each tree limited to a depth of 6 and a learning rate of 0.05 — deliberately matching XGBoost's depth and learning rate exactly, so that any difference observed between the two models' results in Chapter 4 reflects a genuine difference in how the two libraries build and combine their trees internally, rather than simply reflecting different hyperparameter choices.

### 3.10.6 Hybrid Models: SARIMAX + XGBoost, and SARIMAX + CatBoost

**In plain terms:** Both hybrid models in this study combine a statistical model with a machine learning model in a specific two-step way, rather than simply averaging their two separate forecasts together. The intuition is this: SARIMAX (Section 3.10.1) is explicitly built to capture a series' overall trend and seasonal pattern, but — being a fundamentally linear model — it may leave behind a systematic, non-linear pattern in its own mistakes (its "residuals," meaning actual price minus SARIMAX's predicted price) that a more flexible machine learning model could learn to predict. So instead of asking XGBoost or CatBoost to predict the price directly, this project trains them to predict *SARIMAX's own forecasting error* instead, using the same engineered features described in Section 3.8. The final forecast produced by a hybrid model is then simply: **SARIMAX's own forecast, plus the machine learning model's predicted correction to that forecast.**

An analogy may help: imagine one forecaster who is good at spotting the big picture — the general trend and the yearly cycle — but who consistently gets thrown off by short-term, irregular events like a particular week's unusual weather or an especially sharp fuel-price jump. A second forecaster, given access to the first forecaster's track record, specifically studies *when and why* the first forecaster tends to be wrong, and learns to apply a correction on top of the first forecaster's number. The combined answer — first forecaster's estimate, plus second forecaster's learned correction — is often better than either forecaster working alone. This "fit a linear model first, then model its residuals with a flexible machine learning model" design is a well-established and previously validated pattern in the wider forecasting literature (Patil, Shah, Shah, & Kotecha, 2023; Zhao, Chen, Suraphee, Phoophiwfa, & Busababodhin, 2025), and this project's implementation of it follows that same established structure rather than inventing a new one.

**How it was implemented.** Concretely, for a given training window, SARIMAX is fit first (using the same per-vegetable order selected in Section 3.10.1), and its in-sample fitted values are subtracted from the actual training prices to produce a residual series. Either an XGBoost model (using the exact same configuration described in Section 3.10.4) or a CatBoost model (using the exact same configuration described in Section 3.10.5) is then trained to predict that residual series from the engineered features — this is the only difference between the two hybrid variants; everything else about how they are built and evaluated is identical. When a forecast is needed for a new, unseen week, the same lightweight SARIMAX artifact described in Section 3.10.1 produces its own forecast for that week, the residual model separately produces its own predicted correction for that week, and the two numbers are simply added together to produce the hybrid model's final forecast.

It is worth stating plainly, and this is examined properly in Chapter 4, that this two-stage design is only as strong as its first stage: if SARIMAX itself is producing a poor forecast for a given vegetable in a given period, the hybrid model inherits that poor starting point and can only partially correct it, rather than escaping it entirely — this turns out to be a genuinely important and honestly reported finding of this research, not something to be glossed over.

## 3.11 A Shared Training Pipeline

Although the seven model families described in Section 3.10 are built using different libraries and have very different internal mechanics, they are all trained and evaluated through one single shared piece of code (`src/models/common.py`), rather than each model family reimplementing its own separate training loop, its own separate cross-validation logic, and its own separate way of saving results. This was a deliberate engineering and methodological decision: it guarantees that every model family is evaluated under *exactly* the same rules (described fully in Section 3.12), which is what makes a fair, apples-to-apples comparison between them possible in the first place. Concretely, each individual model's own training script only needs to supply two small, model-specific pieces of logic — "given a training set, fit a model of this type and use it to predict a test set" and "given the full dataset, fit and return one final production model" — and the shared pipeline handles everything else: splitting the data correctly, running the walk-forward cross-validation, computing every evaluation metric identically, calculating the prediction interval, and saving both the trained model artifact and its results to disk in a consistent format.

## 3.12 Evaluation Protocol: How Models Were Tested

A central methodological principle followed throughout this research is that a forecasting model must always be tested on data it has genuinely never seen during training — otherwise, a model could simply be "memorising" its training data rather than learning a real, generalisable pattern, and would appear far more accurate than it actually is once deployed on real, future weeks it has never encountered. To enforce this rigorously, each vegetable's roughly 571-row feature-engineered dataset (Section 3.8) is split into three distinct parts, used for three distinct purposes, following the time-series cross-validation approach specified in this project's original research proposal:

**1. The final holdout set — the last 52 weeks (one full year) of data.** This block of the most recent available weeks is set aside completely and is never used, in any way, for training a model or for choosing between different configurations. It exists purely to answer one question at the very end: "how accurately does this fully finished model forecast weeks it has truly never been exposed to at all?" Every headline accuracy number reported in Chapter 4 comes from this holdout set.

**2. Walk-forward cross-validation — the remaining roughly 519 weeks, split into 5 sequential folds.** Ordinary cross-validation, as commonly used for non-time-series data, randomly shuffles data into groups; this cannot be used here, because randomly shuffling weekly price data would let a model be "trained" on future weeks and "tested" on earlier weeks, which is not a realistic test of forecasting ability — a real forecaster can never see the future. Instead, this project uses **walk-forward (or "expanding-window") cross-validation**: the data is split into five sequential blocks, and for each of the five rounds, a model is trained only on all the data *before* a given block, and then tested on that block specifically, before moving forward to the next block (which now includes more historical data than the round before it). This closely mimics how a real forecasting system would actually be used in practice — always trained on the past, always predicting the immediate future — and it is what produces the cross-validation accuracy figures reported alongside the holdout figures in Chapter 4's results tables.

**3. A final production refit — the complete dataset, all ~571 weeks.** After a model's accuracy has been measured using the two steps above, one further, final version of that model is trained one more time using absolutely all of the available historical data, including the 52 holdout weeks that were deliberately excluded during testing. This final version is the one actually saved to disk (under `trained_models/`) and the one that would be used to produce a genuinely new, real-world forecast for next week — since by that point, there is no reason to withhold any real historical data from a model that is actually going to be used, only from a model that is being *evaluated*.

This same three-part protocol — holdout, walk-forward cross-validation, final refit — is applied completely identically to all seven model families and all six vegetables, run automatically end-to-end by a single orchestration script (`scripts/train_all.py`), which produces the full comparison results discussed in Chapter 4.

## 3.13 Evaluation Metrics: How Accuracy Was Measured

Once a model has produced a set of forecasts for the holdout period, those forecasts need to be compared against the actual, real prices that occurred, using a small set of standard numerical accuracy measures. This project reports four such measures for every model and every vegetable, each capturing a slightly different aspect of accuracy, because relying on only one measure can sometimes give a misleading picture on its own.

- **MAE (Mean Absolute Error).** This is simply the average size of the model's mistakes, ignoring whether each mistake was an over-prediction or an under-prediction — calculated by taking the absolute (always-positive) difference between each predicted price and the actual price, for every week in the holdout period, and averaging those differences. If a model's MAE for carrot is, say, 100 rupees, that means its forecasts are, on average, about 100 rupees away from the true price, in either direction. MAE is easy to interpret directly in the same units as the price itself.

- **RMSE (Root Mean Squared Error).** This is calculated similarly to MAE, but each individual error is *squared* before being averaged, and then a square root is taken at the end to bring the result back to the original price units. Squaring has the effect of penalising large errors disproportionately more than small ones — a single very badly wrong forecast will increase RMSE by more than several moderately-wrong forecasts would. RMSE is the specific measure this project uses as the primary basis for deciding which model family is most accurate overall for each vegetable (explained further in Section 3.14), precisely because occasional very large forecasting errors are especially costly and undesirable in a system meant to give farmers actionable advice.

- **MAPE (Mean Absolute Percentage Error).** This expresses the average error as a *percentage* of the actual price, rather than as a raw rupee amount, by dividing each absolute error by that week's actual price before averaging. Because it is expressed as a percentage, MAPE has the advantage of being comparable across vegetables with very different typical price levels (for example, comparing accuracy on an expensive vegetable against accuracy on a cheap one) in a way that a raw rupee-based measure like MAE or RMSE cannot easily do on its own.

- **R² (R-squared, the coefficient of determination).** This measures how much better a model's forecasts are than the simplest possible baseline of just always guessing the holdout period's own average price. An R² of 1.0 would mean the model's forecasts are perfect; an R² of 0.0 would mean the model does no better than simply guessing the average price every single week; and — importantly, and something this project's own results show in several cases in Chapter 4 — a **negative** R² is entirely possible, and means a model's forecasts are actually *worse* than that simple constant-average baseline. This is a genuinely useful measure specifically because it can reveal, honestly, when a model has essentially failed to learn anything useful for a particular vegetable, something MAE, RMSE, or MAPE do not directly convey on their own.

All four measures are calculated using one single shared implementation (`src/evaluation/metrics.py`), used identically by every model's training script and by the final comparison script, so that there is no possibility of two different models being scored by two subtly different formulas.

## 3.14 Prediction Intervals: Communicating Uncertainty, Not Just a Single Number

A single predicted price number, on its own, hides an important piece of information that matters enormously to a farmer deciding whether to trust and act on a forecast: *how much uncertainty surrounds that number*. A forecast of "150 rupees next week" that could realistically turn out to be anywhere from 120 to 180 is a very different, and less confidently actionable, piece of information than a forecast of "150 rupees next week" that has historically turned out to be accurate to within a few rupees. To communicate this honestly, every model's holdout forecasts in this project are accompanied by a **prediction interval** — a lower and upper bound around the point forecast, intended to contain the true future price with a chosen level of confidence (this project uses 80% as that chosen confidence level).

Rather than build seven different, model-specific ways of calculating this interval (which would be considerably more complex — it would require, for example, a fundamentally different statistical technique for SARIMAX than for a neural network like the LSTM, and there is no single standard, well-agreed technique at all for tree-based models like Random Forest), this project uses one single, uniform, **model-agnostic** method that works identically regardless of which of the seven model families produced the underlying forecast, following the general approach to uncertainty quantification for time-series forecasts described by Xu, Mei, Bates, Taylor, and Tibshirani (2023).

**How it works, in plain terms.** During the walk-forward cross-validation process described in Section 3.12, every model, for every fold, produces a set of forecasting errors — the difference between what it predicted and what actually happened, for weeks it had not been trained on. This project pools together *all* of these out-of-sample errors, across all five cross-validation folds, into one combined sample of "how wrong has this model typically been, when tested on data it hasn't seen." From that pooled sample of past errors, the 10th percentile and the 90th percentile are calculated (using the 80% confidence level configured for this project — a different confidence level would use different percentile cut-offs). These two percentile values become a lower offset and an upper offset, which are then simply added to each of the model's holdout-period point forecasts, to produce a lower bound and an upper bound around each individual forecast.

Because these percentile offsets are calculated purely from the *cross-validation* folds — data that comes entirely before the holdout period — and are then applied to, and checked against, the *holdout* period's own actual prices, the holdout period ends up serving a second, independent purpose beyond just testing point-forecast accuracy: it also serves as a genuine, honest test of whether the prediction interval itself is well-calibrated, rather than the interval being tested on the very same data it was built from.

**Measuring how well-calibrated each interval actually is.** The fraction of holdout weeks whose true, actual price fell within a model's predicted lower-to-upper range is calculated and reported as that model's **empirical coverage**. If an interval is well-calibrated, its empirical coverage on the holdout should come out close to the intended 80% confidence level. This project's own results (reported fully in Chapter 4) show that calibration varies considerably from one vegetable to another — for some vegetables it is close to the intended 80%, while for others (particularly the more volatile carrot and brinjal series) it comes out noticeably lower, meaning the interval is, in practice, narrower than it should ideally be for that vegetable. This is reported honestly as a genuine finding of this research, rather than something to gloss over, precisely because a farmer-facing system that claims 80% confidence but is actually right only, say, 55% of the time would be actively misleading rather than merely imprecise.

One known limitation of this approach is worth stating plainly: because the cross-validation folds used to calculate these error percentiles are of different sizes (each fold's training window is larger than the one before it, since this project uses an expanding walk-forward scheme), pooling their errors together treats an early fold's errors — coming from a model trained on comparatively little historical data — as equally representative as a later fold's errors, coming from a model trained on considerably more data. This is a standard, widely accepted simplification in this general style of residual-based interval estimation, but it does mean the resulting interval width is not a perfectly precise match to the true uncertainty of the final, fully trained production model specifically.

## 3.15 Model Selection: Two Different Questions, Two Different Criteria

This research deliberately uses two different criteria to answer two genuinely different questions, and it is important to be explicit about why they are not the same measure used for two purposes.

**Question one: "Which of the seven model families is the most accurate for this specific vegetable?"** This is answered using **holdout RMSE** (Section 3.13) — the actual, out-of-sample forecasting accuracy on a full year of genuinely unseen data. This is the standard, well-established approach for comparing fundamentally different kinds of forecasting models against each other in the wider forecasting literature (an approach also used, for example, in the well-known M-competitions, a series of major international forecasting competitions). It is the only fair choice available here for a specific technical reason: a different, well-known statistical measure called AIC (introduced in Section 3.10.1) is only mathematically well-defined for models like SARIMAX that are fit by directly maximising a likelihood function — there is no standard, agreed way to calculate an AIC score for a Random Forest, an XGBoost model, a CatBoost model, or an LSTM, so AIC simply cannot be used as a common yardstick across all seven model families at once, even though it can be meaningfully used *within* SARIMAX alone.

**Question two: "Given that SARIMAX has been chosen as one of the seven approaches, what specific internal order should it use for a given vegetable?"** This narrower, SARIMAX-internal question is answered using **AIC** instead (Section 3.10.1), because this is the standard, textbook (Box–Jenkins) approach specifically for choosing a statistical time-series model's own internal structure, and it does not require comparing across different types of model at all — only across different orders of the same SARIMAX model.

Keeping these two questions and their two different criteria clearly separate — rather than, for instance, mistakenly trying to use AIC to decide whether SARIMAX or Random Forest is the better overall model for carrot — is a deliberate and important methodological safeguard in this research, and the apparent tension noted in Section 3.10.1 (that the AIC-selected order does not always produce the best holdout RMSE) is exactly the kind of situation this separation is designed to handle correctly: AIC did its job (choosing SARIMAX's best internal structure by the standard statistical method for that specific task), and holdout RMSE separately does its own job (fairly judging SARIMAX, with whatever order AIC gave it, against six entirely different kinds of model).

## 3.16 The Prototype Backend System

Beyond the forecasting research itself, this project also built a working prototype backend system, so that the forecasts, model comparisons, and historical data produced by the pipeline described above are not left sitting only as files on a researcher's own computer, but are instead served through a proper application programming interface (API) that a real web or mobile front-end could connect to. This section explains how that system works, in plain terms.

The backend is a **FastAPI** application — a modern, widely used Python web framework for building APIs — that reads pre-computed forecasts, model comparison metrics, and historical price data out of a **PostgreSQL** database, rather than running any model prediction live, on the fly, for each incoming request. This design choice reflects the actual nature of this system: forecasts are produced by the training pipeline described throughout this chapter on a periodic (currently manual, eventually weekly-automated) basis, not instantly recalculated the moment someone asks for one, so there is no need for the API itself to run any machine learning code directly — its job is simply to serve up the results that the training pipeline has already produced and stored.

The database is organised into three main tables: one holding historical prices (mirroring the processed per-vegetable CSV files described in Section 3.6), one holding the actual forecasts (predicted price, plus the prediction-interval lower and upper bounds described in Section 3.14, for every vegetable and every model family), and one holding each model's evaluation metrics (MAE, RMSE, MAPE, R², and prediction-interval calibration, as described in Sections 3.13–3.14). A dedicated script (`app/backend/seed.py`) transfers data from the same CSV files the training pipeline produces into this database, and is written so that it can be safely re-run after every retrain without creating duplicate rows — it updates existing records rather than blindly re-inserting them.

To keep the API fast under repeated requests, a **Redis** cache sits in front of the database: the first time a particular piece of data (for example, "the latest forecast for carrot") is requested, it is fetched from PostgreSQL and then also stored in Redis's fast in-memory cache for a period of seven days (matching how often the underlying data is expected to actually change, given the weekly retraining cadence); any further requests for that same data within that window are served directly from the cache, without needing to query the full database again. Whenever the underlying data is refreshed by re-running the seed script, this cache is explicitly cleared for the affected vegetable, specifically to avoid a subtle but real risk: silently serving stale, out-of-date cached results to a user after new data has actually already arrived.

The API exposes several endpoints (specific web addresses that return a particular piece of data), including: a health-check endpoint to confirm the database and cache are both reachable; an endpoint listing the six target vegetables; an endpoint returning the full model-comparison metrics for a given vegetable; an endpoint returning the single most recent forecast for a vegetable (either from a specific named model, or automatically from whichever model currently has the lowest RMSE for that vegetable); and endpoints for retrieving filtered, paginated forecast history and historical price history. Every endpoint is documented with a human-readable description directly inside the code, which FastAPI automatically turns into a live, interactive documentation page, so that another developer can understand and try out the full API without needing to read the underlying source code at all. The backend's correctness is also verified by an automated test suite covering both expected, everyday use and deliberately awkward edge cases (unknown vegetable names, invalid pagination values, and so on), run against a real, seeded copy of the database and cache rather than a simulated stand-in for them.

## 3.17 Implementation Environment and Reproducibility

This entire pipeline — from data collection through to a trained model and a running backend API — is implemented in **Python 3.13**, inside its own isolated project environment (a Python "virtual environment," which keeps this project's exact library versions separate from any other Python software already installed on the same computer, avoiding version conflicts). The prototype backend deliberately uses its own, entirely separate environment from the main research pipeline, since it depends on a different, non-overlapping set of libraries (a web framework and database drivers, rather than machine learning libraries).

Every dependency this project relies on — every library named in Section 3.9 — is listed with a specific, pinned set of versions in a single requirements file, so that the exact same software environment can be recreated by another researcher, or by this project's own author on a different machine, at a later date. All results reported in this thesis were produced on a single physical machine (an Apple Silicon-based Mac), and the full 42-model training grid (seven model families times six vegetables) completes in roughly 10 to 15 minutes end-to-end, run through one single orchestration script (`scripts/train_all.py`) that trains every model, evaluates it, and writes out the combined comparison tables and prediction records used throughout Chapter 4 — meaning the entire experiment described in this chapter can be reproduced, from a clean checkout of the project's code, with a small number of straightforward commands, rather than requiring any manual, undocumented steps.

## 3.18 Summary of the Methodology

To summarise the whole chapter in one place: this research collects raw vegetable price data from HARTI's weekly government bulletins, weather data from the Open-Meteo historical archive, and fuel price data from Ceylon Petroleum Corporation's published price-revision history, using purpose-built automated scrapers (Section 3.4); passes all of this raw data through an automated data-quality gate that checks for missing weeks and implausible outlier values before anything is trusted (Section 3.5); merges the three sources together into one clean, aligned dataset per vegetable, matched to each vegetable's representative growing district for weather purposes (Section 3.6); explores that data visually and statistically to understand its trends, seasonality, and relationships before modelling it (Section 3.7); engineers a shared set of lagged, rolling, calendar, and exogenous features used identically by every model (Section 3.8); trains and fairly compares seven distinct forecasting approaches — SARIMAX, LSTM, Random Forest, XGBoost, CatBoost, and two SARIMAX-residual hybrid models — for each of six target vegetables, using an identical walk-forward cross-validation and holdout evaluation protocol for every model (Sections 3.10–3.12); measures accuracy using four standard, complementary metrics and adds an honestly-calibrated prediction interval to every forecast (Sections 3.13–3.14); and finally serves the resulting forecasts, comparisons, and historical data through a working prototype API backed by a real database and cache (Section 3.15). The next chapter (Chapter 4) presents and discusses the actual results this methodology produced.
