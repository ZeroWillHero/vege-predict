# VegePredict Backend — Setup, Migration & Deployment

FastAPI + Postgres + Redis API serving pre-computed forecasts, model comparisons, and
historical prices. See the root `CLAUDE.md`'s `## Backend API` section for architecture,
schema, endpoint, and gotcha details — this doc is the operational how-to.

Standalone service: its own `requirements.txt` and `.venv`, separate from the research
pipeline's root `.venv`. Always use `app/backend/.venv/bin/python3` for backend commands,
never the root venv.

## 1. Local setup

```bash
cd app/backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

### Infrastructure (Postgres + Redis via Docker)

Local dev expects two already-running Docker containers (not started by this project's
tooling):

```bash
docker run -d --name postgres -p 5432:5432 \
  -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=pg123 -e POSTGRES_DB=vegepredict \
  postgres:15.17-trixie

docker run -d --name Redis-main -p 6379:6379 redis:7-alpine
```

If they already exist but are stopped:

```bash
docker start postgres Redis-main
```

Verify both are up:

```bash
docker exec postgres pg_isready -U postgres -d vegepredict
docker exec Redis-main redis-cli ping
```

Connection strings default to the local values above (`app/backend/config.py`). To point
at a different Postgres/Redis, create `app/backend/.env` (gitignored):

```bash
VEGEPREDICT_DATABASE_URL=postgresql+asyncpg://user:pass@host:5432/vegepredict
VEGEPREDICT_REDIS_URL=redis://host:6379/0
VEGEPREDICT_JWT_SECRET=some-long-random-value   # required in any non-local environment
VEGEPREDICT_JWT_EXPIRE_MINUTES=60               # optional, defaults to 60
```

`config.py` ships a dev-only default `jwt_secret` so local setup works out of the box —
**always override it via `VEGEPREDICT_JWT_SECRET` outside local dev.**

## 2. Run database migrations

Migrations are managed with Alembic (`app/backend/alembic/`).

```bash
cd app/backend
.venv/bin/python3 -m alembic upgrade head
```

Other useful Alembic commands:

```bash
# Check current DB revision vs. latest available
.venv/bin/python3 -m alembic current
.venv/bin/python3 -m alembic history

# After changing a model in models/, generate a new migration (review the
# autogenerated file before applying — see CLAUDE.md's Backend API gotchas)
.venv/bin/python3 -m alembic revision --autogenerate -m "describe the change"
.venv/bin/python3 -m alembic upgrade head

# Roll back one revision
.venv/bin/python3 -m alembic downgrade -1
```

## 3. Seed / migrate data into Postgres

`seed.py` is an idempotent ETL: reads the research pipeline's CSV outputs and
upserts them into Postgres, then invalidates the relevant Redis cache entries.

```bash
# From the project root (not app/backend/), so the app.backend.* imports resolve
app/backend/.venv/bin/python3 app/backend/seed.py
```

What it loads, and where from:

| Table | Source | Produced by |
|---|---|---|
| `historical_price` | `data/processed/<vegetable>.csv` | `src/data_processing/build_dataset.py` |
| `forecast` (backtest rows) | `results/metrics/holdout_predictions.csv` | `scripts/train_all.py` |
| `forecast` (future rows) | `results/metrics/future_predictions.csv` (if present) | `scripts/predict_future.py` |
| `model_metric` | `results/metrics/all_results.csv` | `scripts/train_all.py` |

Safe to re-run any time after a retrain or a new `predict_future.py` run — every insert is
an `ON CONFLICT DO UPDATE` upsert on the table's natural key, and any forecast row still
missing an `actual_price` gets backfilled automatically from `historical_price` once that
week's real price is known.

**Full pipeline (rebuild data → retrain → forecast → seed) in one shot**, useful against a
remote database:

```bash
./scripts/run_pipeline_and_seed_remote.sh
```

Reads `REMOTE_DATABASE_URL`/`REMOTE_REDIS_URL` env vars if set, otherwise uses the defaults
baked into the script. See the script's header comment for what each of its 5 steps does.

## 4. Create the first user account

There is no public self-registration — every account after the first is created via
`POST /users` by an existing admin/superadmin. The very first superadmin has to be created
directly:

```bash
# Interactive password prompt
app/backend/.venv/bin/python3 app/backend/create_superadmin.py \
  --email you@example.com --first-name Ada --last-name Lovelace

# Or non-interactively (e.g. scripted setup) — password never appears as a CLI arg
VEGEPREDICT_SUPERADMIN_PASSWORD='...' app/backend/.venv/bin/python3 app/backend/create_superadmin.py \
  --email you@example.com --first-name Ada --last-name Lovelace
```

Idempotent — re-running with the same email promotes/reactivates that account to
superadmin rather than erroring. See `CLAUDE.md`'s `### User Management & Auth` section for
the full role/permission model.

## 5. Run the API

```bash
# From the project root, so app.backend.* absolute imports resolve
app/backend/.venv/bin/python3 -m uvicorn app.backend.main:app --reload --port 8000
```

- Swagger UI: `http://localhost:8000/docs`
- ReDoc: `http://localhost:8000/redoc`
- Health check: `curl http://localhost:8000/health` — should return `{"status":"ok","database":true,"redis":true}`

Log in via `/docs`'s "Authorize" button (or `POST /auth/login` directly) using the
superadmin credentials from step 4 to try the authenticated `/users*` endpoints.

## 6. Run tests

Hits the real seeded Postgres/Redis (no mocks) — steps 1–3 above must have been done first.

```bash
app/backend/.venv/bin/python3 -m pytest app/backend/tests/ -c app/backend/pytest.ini

# Single test file / test
app/backend/.venv/bin/python3 -m pytest app/backend/tests/test_users.py -c app/backend/pytest.ini
app/backend/.venv/bin/python3 -m pytest app/backend/tests/test_auth.py::test_login_success -c app/backend/pytest.ini
```

## 7. Deploying (EC2 via GitHub Actions)

Pushes to `main` trigger `.github/workflows/deploy.yml`: builds the API image, pushes to
GHCR, syncs `docker-compose.yml` + `deploy/` to the EC2 host, then runs
`deploy/pull-and-deploy.sh` there, which pulls the new image, runs
`docker compose up -d`, applies migrations (`alembic upgrade head` inside the `api`
container), and reloads nginx.

Manual deploy step on the server, if ever needed directly:

```bash
ssh <server>
cd ~/Research-Project
export API_IMAGE=ghcr.io/zerowillhero/vege-predict-api:latest
deploy/pull-and-deploy.sh
```

Seeding the **remote** database (data/forecasts aren't part of the deploy workflow — that's
a separate, manually-triggered step, or via `scripts/run_pipeline_and_seed_remote.sh` from a
machine with the research pipeline + trained models available):

```bash
REMOTE_DATABASE_URL=postgresql+asyncpg://postgres:pg123@<ec2-host>:5432/vegepredict \
REMOTE_REDIS_URL=redis://<ec2-host>:6379/0 \
  ./scripts/run_pipeline_and_seed_remote.sh
```

## Troubleshooting

- **`ModuleNotFoundError` on `app.backend.*`** — you ran the command from inside
  `app/backend/` instead of the project root, or used the wrong venv. Always run backend
  Python commands from the project root with `app/backend/.venv/bin/python3 ...`.
- **Alembic can't connect / wrong DB** — check `app/backend/.env` (or the
  `VEGEPREDICT_DATABASE_URL` env var) points at the intended Postgres instance; `alembic
  current` shows what it's actually connected to.
- **bcrypt/passlib error (`password cannot be longer than 72 bytes` or `__about__`
  AttributeError)** — `passlib` 1.7.4 is incompatible with `bcrypt>=4.1`; `requirements.txt`
  pins `bcrypt<4.1` for this reason. Re-run `pip install -r requirements.txt` if you see
  this after a fresh install picked up a newer `bcrypt`.
- **API serving stale data after a reseed** — `seed.py` invalidates Redis automatically on
  every run; if you bypassed `seed.py` and wrote to Postgres directly, cached JSON can be up
  to 7 days stale (`cache_ttl_seconds`). Restart Redis or call
  `app.backend.services.cache_service.invalidate_all()`/`invalidate_vegetable()` manually.
